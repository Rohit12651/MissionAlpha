# ADR-050 — On-Demand Agent Minting for Out-of-Scope Stacks

**Status:** Accepted  
**Date:** 2026-06-21  
**Deciders:** Architect, CEO, Senior Security Engineer  
**Relates to:** ADR-037 (execution sandbox), ADR-038 (full tool loop), ADR-039 (approval UX), ADR-041 (audit trail)

---

## Context

The MissionAlpha swarm has 16 fixed builtin agents covering Python/FastAPI backends, TypeScript/React frontends, Expo/React Native mobile, MongoDB, GCP/Docker CI-CD, and QA. When a feature requires a stack outside this set (e.g. Go microservice, Angular admin panel, Rust CLI), no installed agent has the competence to write and test code correctly. The options are:

1. Use the nearest-fit builtin (lower competence, risk of wrong idioms).
2. Block until a human writes the code.
3. Mint a new agent on demand, scoped to the gap, running inside the existing jail.

---

## Decision

**GO with option 3 — on-demand minting, behind a USER-gated flow and a six-guard security gate.**

The minted agent:
- Holds a `dev:true` skill from the closed `SKILL_CATALOG` (e.g. `code-implement-go`).
- Its persona **redirects** to an installed specialist (e.g. `golang-pro`) for stack competence — the minted agent is a routing + approval shell, not a standalone expert.
- Writes code via `/run` (sandbox worktree, Write/Edit tools).
- Builds/tests via the **existing** `/exec` Docker broker — no new exec path.
- All exec calls are **approval-forced** (G1) regardless of command classification.

---

## Flow

```
architect → docs/plans/<feature>-stack-manifest.json
   ↓
CEO: POST /runtime/factory/detect-gaps {manifest}   ← READ-ONLY advisory
   ↓  gaps found
CEO surfaces CAPABILITY_GAP in agent-status/CEO/CAPABILITY_GAPS.md + heartbeat
   ↓
USER GO  → factory.createAgent(devSpec)
USER NO-GO → use nearest-fit builtin
   ↓ (GO path)
Minted agent writes code (sandbox) → /exec for build/test (jailed, approval-forced)
Operator approves → runs in existing Docker jail
```

## Security Gate — G1 through G6 (ALL BLOCKING)

These guards were implemented before any catalog or exec coupling. All six must be green before Section A/B ships.

| Guard | What it enforces | Where |
|---|---|---|
| **G1** | Factory agents never auto-run any exec, even "safe" class | `tool-broker.mjs` `decide()` |
| **G2** | Factory agents default-deny network in containers | `tool-broker.mjs` `execTool()` |
| **G3** | Factory tier explicitly stamped in audit records (`tier:"factory"` vs `tier:"builtin"`) | `tool-broker.mjs` + `factory.mjs` |
| **G4** | Dev skills grant only `{Read, Write, Run}` — no Bash, no MCP, no SEED_DIRS/CONFIG_GUARD changes | `factory.mjs` `SKILL_CATALOG` |
| **G5** | `--allowed-tools` bound from validated spec at spawn frame, before any stdin write | `server.mjs` `cliReply()` + `engineDispatch()` via `agent-tools.mjs` |
| **G6** | Dev skill `redirect` must be in `SPECIALIST_ALLOWLIST` (closed set of vetted specialist ids) | `factory.mjs` `validateSpec()` |

**B2 runtime gate (exec-capability gate):** factory agents without a `dev:true` skill receive HTTP 403 on `POST /:id/exec` — the content-posting tier cannot reach the sandbox at all.

---

## Key Design Decisions

### Reuse the existing jail (no new exec path)

The Docker sandbox in `sandbox.mjs` is already hardened (ADR-037). Routing a minted agent through the existing `/exec` broker inherits all jail properties: network-default-deny, read-only host filesystem, `/work` bind mount, container image pinned by tag. No new attack surface.

### Redirect pattern (not a standalone expert)

A minted `code-implement-go` agent is NOT a Go expert. Its persona explicitly delegates to `golang-pro` for stack guidance. This keeps the minted agent lightweight and auditable: its system prompt is entirely generated by `buildSystemFor()` from the validated spec, with the redirect directive and tool note injected by the server. No free-text injection path.

### USER GO is mandatory — no auto-mint

`POST /runtime/factory/detect-gaps` is strictly read-only and never calls `createAgent`. The CEO surfaces the gap report to USER; USER must explicitly approve. This preserves the human-in-the-loop invariant that governs all agent creation.

### Capability index is static + pure

`capabilityIndex()` returns a frozen snapshot of the 16 builtins' stacks. It has no I/O and takes no parameters. Minted agents are not automatically added to the index (the endpoint is advisory). Tests are deterministic.

## Alternatives Considered

| Alternative | Rejected because |
|---|---|
| Use nearest-fit builtin | Wrong idioms for non-Python/TS stacks; QA will flag bad code |
| Block on human intervention | Defeats the autonomy goal; blocks the swarm for days |
| Auto-mint without USER GO | Violates the factory security model (F3 gate); CEO must surface gaps |
| New exec path per language | Unnecessary complexity; the existing jail is language-agnostic |
| Give minted agent full MCP | G4 guard: MCP coupling from exec capability is explicitly blocked; default-deny holds |

---

## Accepted Residual Risks

| Risk | Acceptance rationale |
|---|---|
| `chmod 0o777` host-side `/work` exposure | Single-operator / CI scope; not multi-tenant |
| Sandbox image pinned by tag, not digest | Acceptable for dev agents; prod path can add digest pinning |
| Per-destination egress filtering deferred when network granted | G2 default-deny covers the common case; full egress filtering is a Phase 5 item |
| Redirect degrades to persona-text in headless `-p` turns if specialist subagent is uninvocable | Redirect is a persona directive, not a hard dependency; lower competence is tolerated |

---

## Consequences

- **Positive:** Out-of-scope stacks unblock without human code authoring; the existing jail's security properties are inherited.
- **Positive:** Content-posting agents (no dev skill) cannot reach `/exec` even if compromised — the capability gate is a hard runtime wall.
- **Negative:** Minted agents are less capable than native specialists; the redirect pattern mitigates but does not eliminate this.
- **Negative:** Each new stack requires a new SKILL_CATALOG entry + SPECIALIST_ALLOWLIST entry — intentional friction to keep the catalog auditable.
